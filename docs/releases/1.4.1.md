# Better SignalRGB Screen Capture 1.4.1

This update fixes the capture-stage loss of HDR highlights for **display, window and region sources**. It preserves floating-point pixels until conversion to the SDR images used by the application's preview, web output, SignalRGB and native OpenRGB output.

## Changes

- **FP16 screen capture:** Windows Graphics Capture and Win2D retain linear scRGB values above ordinary SDR white through capture and resizing. HDR-to-SDR conversion happens before the first JPEG encoding, where the previous BGRA8 capture could already have clipped bright detail.
- **Per-display conversion:** Windows HDR mode and SDR reference white determine the conversion. Regions crossing HDR and SDR monitors use separate calibrated tiles before assembly, including negative desktop coordinates and empty areas outside physical monitors. Window capture follows its current display's color information.
- **Region setup preview:** the selection dialog uses the same FP16 backend and HDR/SDR conversion as live capture, with a bounded single-frame preview and cancellation cleanup.
- **No discarded H.264 screen carrier:** display, window and region previews use the new capture backend directly. Webcam capture retains ScreenRecorderLib; this patch does not upgrade that dependency.
- **Honest color diagnostics:** each source reports its backend, SDR/HDR conversion state and available reference white. Unknown HDR mode does not trigger an assumed HDR correction. Confirmed HDR without a readable white level uses neutral exposure and remains diagnostically unknown.
- **Shared normalized source images:** editor preview, web and SignalRGB images, and the native composite originate from the same SDR conversion. Existing output resolutions, JPEG quality and appearance settings remain distinct; this does not promise identical rasterization across outputs.
- **Capture lifecycle:** a resized source recreates its frame pool after releasing borrowed frames and waits for valid new-size content. Cleanup releases the remaining graphics resources even if one disposal fails.
- **Settings layout:** the native OpenRGB label and activation switch use separate layout cells, with a stacked header in narrow windows. About keeps its issue-report link, removes the two Microsoft Store links and has extra space below the last card.

## Color behavior and limits

Sources on known SDR displays bypass HDR exposure and highlight compression. The HDR curve preserves lower tones and reserves room for brighter highlights: normalized HDR reference white maps to approximately 240/255 in sRGB. This is a fixed SDR representation, not a reproduction of an HDR panel's peak brightness or proprietary tone mapping. Existing hue, picture modes, saturation and halo intensity still apply afterward and can independently saturate colors.

**Wallpaper Engine's isolated GDI `PrintWindow` capture remains 8-bit and cannot preserve HDR highlights.** The new screen backend does not make that source HDR-correct. WebView screenshots and webcams retain their existing color paths and are not tone-mapped a second time. Lowering halo brightness cannot reconstruct detail lost in an 8-bit capture.

The new code does not change Windows HDR settings, move application windows or modify Wallpaper Engine's playback settings. FP16 capture uses more intermediate precision; capture, GPU readback, CPU conversion and JPEG encoding still have a cost. There is no zero-copy or universal frame-rate claim.

## Validation

- **2,759 synthetic HDR assertions** pass: reference-white normalization, continuous highlight shoulder, gamut compression, SDR roundtrip, all Half bit patterns, buffer limits and unknown-metadata policy.
- **247 ViewModel assertions** pass, including ten color-diagnostic checks for transitions, immutable snapshots, stopped/failed sessions and stale callbacks.
- 2,233 regression assertions and 81 new capture-service/region-preview assertions pass. The WinUI application builds successfully on Windows x64.
- Actual Win2D GPU textures preserve values above one through FP16 resizing/readback. Real capture tests cover the HDR monitor, HDR/SDR regions across a monitor boundary, negative coordinates and empty desktop areas. A synthetic window preserves gray 128 and maps reference white to 240 at three changing sizes, with repeated start/cancel checks passing on x64 and x86. Real one-shot region previews also pass, including worker shutdown before return.
- One bounded local HDR-monitor capture produced **73 frames in about six seconds at 800×600**, approximately **12.1 fps for a 15-fps request**. This is a machine-specific capture observation, not a 60-fps guarantee or a capture-to-light latency measurement.

The [HDR conversion contract](https://github.com/Fefedu973/Better-SignalRGB-Screen-Capture/blob/1.4.1/tests/BetterSignalRGB.HdrTests/README.md) and [GPU capture harness](https://github.com/Fefedu973/Better-SignalRGB-Screen-Capture/blob/1.4.1/tests/BetterSignalRGB.GraphicsTests/README.md) describe reproduction commands and limits. Pure tests do not replace hardware HDR validation; the legacy ScreenRecorderLib screen-capture tests do not validate this new backend. Physical screen/LED measurements, HDR mode switches during capture and ARM64 runtime behavior are not covered by these local checks.
